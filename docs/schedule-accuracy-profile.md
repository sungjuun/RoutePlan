# 일정 정확도·프로필 사진·알림 (V18)

## 사용 방법

- 마이페이지 → **사진 선택 → 사진 저장**. PNG/JPEG 최대 2MB, 가로·세로 4096px 및 1600만 화소 이내. 가운데 정사각형을 256px PNG로 재인코딩해 저장하며, **기본 이미지**로 삭제할 수 있습니다. 헤더와 마이페이지에 즉시 반영됩니다.
- 헤더의 **벨 아이콘** → 최근 30개 알림, 읽지 않은 개수, 모두 읽음, 전체 비우기. 일반 성공 알림은 하단에 뜨지 않습니다. 오류는 닫을 수 있는 상단 안내와 알림함에 표시됩니다. 알림은 메모리만 사용하고 새로고침·로그아웃 때 비워집니다.
- 일정 보기 → 실제 여행 데이터 → **날씨를 3시간마다 자동 갱신**. 기본은 꺼짐이며 여행마다 선택합니다. 서버 실행 중 예보 범위 안에 들어온 여행을 갱신합니다. **갱신 상태 확인**에서 최근 성공 시각·실패 안내를 확인합니다. 새 예보로 일정까지 바꾸려면 새 계산 또는 날씨 사유 재최적화를 실행합니다.

## 영업시간 정확도

Google Details 필드: `id,regularOpeningHours,currentOpeningHours,utcOffsetMinutes`.

1. 주간 구간을 일별 분 단위 `[시작, 종료)` 목록으로 정규화합니다. 1440은 다음 자정입니다.
2. 분할 영업 사이의 휴식 시간은 방문할 수 없습니다. 겹치거나 맞닿은 구간만 병합하고 전체 체류가 한 구간에 들어가야 합니다.
3. 야간 영업과 토요일→일요일 연결을 각각 날짜에 배분합니다. 여행의 일일 시작/종료는 기존처럼 같은 날짜 안이어야 합니다.
4. 제공된 특별 영업시간은 장소 현지 오늘부터 6일 뒤까지 우선합니다. 해당 범위에 구간이 없는 날은 휴무입니다. 그 밖은 정규 시간을 적용하고 휴일 확인 경고를 남깁니다. 원본 영업시간은 캐시·영구 저장하지 않습니다.
5. 기존 수동 요일 영업시간/휴무 설정을 덮어쓰지 않습니다. 수동 API 자체는 여전히 요일별 한 구간입니다. Google 정보 누락이나 불완전한 형식은 경고하며 실제 영업을 보장하지 않습니다.

범위 근거: [Google Places OpeningHours](https://developers.google.com/maps/documentation/places/web-service/reference/rest/v1/places).

## 실제 출발 시각별 대중교통

기본 fallback은 기존 날짜별 Matrix로 방문 순서를 생성한 후, 최종 선택된 방문을 순서대로 다시 계산합니다. 대중교통의 각 구간은 현지 방문 종료 시각을 UTC로 변환한 `departureTime`을 사용합니다. 대기·체류·숙소 귀환까지 다시 합산하며 새 일정 생성과 재최적화에 모두 적용합니다. 완료된 기존 방문은 그대로 둡니다. V25의 선택 기능을 켜면 이 단계보다 먼저 시간 Matrix 기반 날짜·순서 전역 재탐색을 시도합니다.

- 고정 순서 fallback은 Google PUBLIC_TRANSIT만 적용합니다. V25 시간 의존 전역 재탐색은 Google 자동차와 대중교통을 지원합니다.
- fallback의 각 구간은 1×1 Matrix로 조회합니다. 자동차·대중교통 경로는 좌표·방향·이동수단·기본 15분 출발 버킷으로 Redis/PostGIS TTL 캐시를 사용합니다.
- 최대 `선택 방문 수 × 2 + 계획 일수`개 추가 요소(같은 좌표 제외), 검증 루프 45초 제한입니다. 추가 요소·요청 수·시간은 일정 Matrix 측정값에 합산하며 실제 재시도는 기존 월별 사용량 가드가 매번 차감합니다. 네트워크 진행 중 요청의 timeout은 기존 HTTP 설정을 따릅니다.
- fallback에서는 방문 순서와 날짜 배치를 고정합니다. 시간창/귀환 제약을 넘기는 선택 장소는 제외하고 필수 장소가 불가능하면 새 버전을 저장하지 않습니다. 전역 재탐색의 비용·상태 상한과 fallback 조건은 [V25 안내](time-dependent-routing.md)를 확인하세요.
- 현재 기준 과거 7일~미래 100일 및 DST 모호 시각 검사는 유지합니다. [Google 대중교통](https://developers.google.com/maps/documentation/routes/transit-route).

## 날씨 작업과 저장 안전성

- 1분마다 최대 5개 만기 여행을 DB에서 원자적으로 선점합니다. 15분 임대·토큰 검사로 여러 작업자와 취소/갱신 경합을 처리합니다. 정상 갱신 후 3시간, 실패 후 30분 뒤 재시도합니다.
- 여행 기간을 바꿨거나 위치·시간대가 조회 중 변경되면 기존 입력 검사를 통해 쓰기를 거부합니다. 갱신을 끄면 진행 중 응답도 반영하지 않습니다.
- `MANUAL` 예보, 직접 지정한 시간대, 저장된 일정 버전은 정기 작업이 변경하지 않습니다. 실패 시 마지막 성공 예보를 유지합니다. 별도 **날씨 자동 조회** 버튼은 종전처럼 시간대를 자동 감지할 수 있습니다.
- Compose 환경변수 `ROUTEPLAN_WEATHER_AUTO_REFRESH_ENABLED=false`는 작업자 전체를 끕니다. 격리 E2E는 이를 끄고 실제 외부 API를 호출하지 않습니다.
- Open-Meteo 성공 응답의 15분 캐시는 유지합니다. 여러 서버·수동 호출을 합한 공급자 계정 한도를 보장하는 전역 쿼터 장치는 아니며 상용 운영 시 계약·한도를 검토해야 합니다. [모델 갱신 주기](https://open-meteo.com/en/docs/model-updates).

## API와 데이터

| API | 권한/동작 |
|---|---|
| `GET /api/v1/profile/avatar` | 로그인한 본인의 이미지, PNG, no-store |
| `PUT /api/v1/profile/avatar` | CSRF + multipart `file`, 검사·재인코딩 후 교체 |
| `DELETE /api/v1/profile/avatar` | CSRF + 본인 이미지 삭제 |
| `GET /api/v1/auth/me` | `user.profileImageUrl` 포함 |
| `GET/PUT /api/v1/trips/{id}/weather/auto-refresh` | 여행 소유자만 조회/설정, PUT `{ "enabled": true }` |

Flyway **V14**에 `user_avatars`, `trip_weather_refresh`를 추가합니다. 앱 버전 번호와 마이그레이션 번호는 별개입니다. 사진은 로컬 파일 경로나 외부 URL을 받지 않고 PostgreSQL에 저장하므로 컨테이너 재생성 후에도 남습니다. EXIF/원본 메타데이터와 원본 파일은 저장하지 않고 사진을 Google/Open-Meteo로 전송하지 않습니다. 현재 프로필 사진은 본인 화면 전용이며 공개 커뮤니티 아바타 기능은 포함하지 않습니다.

## 검증

2026-08-28 최종 실행: 백엔드 113개, 프론트 39개, Chromium/모바일 E2E 7개 통과. 프론트 lint·production build 통과. 로컬 Compose에 V14 마이그레이션과 새 이미지를 반영하고 백엔드 health `UP`·프론트 HTTP 200 및 기존 여행 #5/#11 보존을 확인했습니다. 실제 인앱 브라우저에서도 모바일 벨 알림함, 가로 넘침 없음, 콘솔 오류 없음과 하단 알림 제거를 확인했습니다. 개발 계정의 사진은 변경하지 않았으며 사진 업로드 검증은 격리 E2E 계정에서 수행했습니다.

Java 단위·API 통합 테스트: 분할/야간/휴일 범위, 출발 시각과 재검증 제외, 이미지 형식·용량·화소 제한, 인증·CSRF·다른 계정 격리, 주기·실패 재시도·갱신 취소 경합. 프론트 테스트: 사진 선택/검증/저장/초기화, 알림 읽음/비우기/Escape, 자동 예보 설정. 브라우저 E2E: 회원가입·여행·커뮤니티 기존 흐름과 사진 저장→새로고침→초기화 및 모바일 알림함.

이 변경의 테스트는 외부 응답을 통제한 회귀 검증입니다. 이전 [실호출 기록](live-validation-2026-08-28.md)은 V17 표본이며, 이번 변경을 실 Google 운행·공휴일 전체와 비교 검증한 결과로 해석하면 안 됩니다.
